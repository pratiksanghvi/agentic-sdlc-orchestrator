# URL Shortener Service with Click Analytics

## Functional requirements

- **FR-1** [MVP] A client can submit a long URL and receive a newly created short link identified by a short code. _(source: clarification)_
  - AC-1.1: Given The service is running, when A client submits a create request with the long URL https://example.com/some/long/path, then The response has a 2xx status and its body contains a non-empty short code
  - AC-1.2: Given A short link was just created for https://example.com/some/long/path, when The client requests the details of the returned short code, then The response has status 200 and the original URL equals https://example.com/some/long/path
- **FR-2** [MVP] Requesting an existing short code redirects the client to the original long URL associated with that short code. _(source: clarification)_
  - AC-2.1: Given A short link exists for https://example.com/target, when A client requests the redirect for its short code without following redirects, then The response Location header equals https://example.com/target
- **FR-3** [MVP] The redirect response uses HTTP status 302 (temporary redirect). _(source: clarification)_
  - AC-3.1: Given A short link exists for https://example.com/target, when A client requests the redirect for its short code without following redirects, then The response status code is exactly 302
- **FR-4** [MVP] A client can retrieve the details of an existing short link by its short code. _(source: clarification)_
  - AC-4.1: Given A short link exists with short code S, when A client requests the details for short code S, then The response has status 200 and the returned short code equals S
- **FR-5** [MVP] The service keeps a total click count for each short link, incremented by one on each successful redirect. _(source: clarification)_
  - AC-5.1: Given A newly created short link with 0 clicks, when A client performs the redirect 3 times and then requests the link's analytics, then The analytics response reports a total click count of 3
  - AC-5.2: Given Two short links A and B exist, each with 0 clicks, when A client performs the redirect for A twice and for B once, then requests analytics for both, then Analytics report 2 clicks for A and 1 click for B
- **FR-6** [MVP] The service records the timestamp of the most recent click (successful redirect) for each short link. _(source: clarification)_
  - AC-6.1: Given A newly created short link, when A client records time T1, performs one redirect, records time T2, and requests the link's analytics, then The last-click timestamp is present and is greater than or equal to T1 and less than or equal to T2
  - AC-6.2: Given A short link that has been clicked once with last-click timestamp L1, when A client performs another redirect after L1 and requests the analytics again, then The new last-click timestamp is later than L1
- **FR-7** [MVP] A client can retrieve a short link's analytics, consisting of the total click count and the last-click timestamp, through a separate per-link API call. _(source: clarification)_
  - AC-7.1: Given A short link exists with short code S that has been clicked once, when A client calls the analytics operation for short code S, then The response has status 200 and contains a total click count of 1 and a non-null last-click timestamp
- **FR-8** [MVP] Short codes are always generated by the service; clients cannot supply a custom alias. _(source: assumption)_
  - AC-8.1: Given The service is running, when A client creates two short links for different long URLs, then Both responses contain service-generated short codes and the two short codes are different
- **FR-9** [MVP] Each create submission produces a new, independent short link with its own short code and click count, even when the same long URL was submitted before. _(source: assumption)_
  - AC-9.1: Given The service is running, when A client submits the same long URL https://example.com/dup in two separate create requests, then The two responses contain different short codes
  - AC-9.2: Given Two short links A and B were created for the same long URL, when A client performs the redirect for A once and then requests analytics for A and B, then Analytics report 1 click for A and 0 clicks for B
- **FR-10** [MVP] Only absolute http or https URLs are accepted when creating a short link; any other value is rejected with a client error (4xx) response and no short link is created. _(source: assumption)_
  - AC-10.1: Given The service is running, when A client submits a create request with the value ftp://example.com/file, then The response status is in the 4xx range and no short code is returned
  - AC-10.2: Given The service is running, when A client submits a create request with the relative value /just/a/path, then The response status is in the 4xx range and no short code is returned
  - AC-10.3: Given The service is running, when A client submits a create request with http://example.com, then The response has a 2xx status and contains a short code
- **FR-11** [MVP] A short link's details include the short code, the original long URL and the creation timestamp. _(source: assumption)_
  - AC-11.1: Given A client recorded time T1, created a short link for https://example.com/details, and recorded time T2, when The client requests the details for the returned short code, then The response contains the short code, the original URL https://example.com/details, and a creation timestamp between T1 and T2 inclusive
- **FR-12** [MVP] The redirect, details and analytics calls return 404 Not Found for a short code that does not exist. _(source: assumption)_
  - AC-12.1: Given No short link exists with short code doesnotexist123, when A client requests the redirect for doesnotexist123, then The response status is 404
  - AC-12.2: Given No short link exists with short code doesnotexist123, when A client requests the details for doesnotexist123, then The response status is 404
  - AC-12.3: Given No short link exists with short code doesnotexist123, when A client requests the analytics for doesnotexist123, then The response status is 404
- **FR-13** [MVP] For a short link that has never been clicked, analytics report a click count of 0 and a null or absent last-click timestamp. _(source: assumption)_
  - AC-13.1: Given A short link was just created and never redirected, when A client requests its analytics, then The response reports a click count of 0 and the last-click timestamp is null or absent
- **FR-14** [MVP] Every successful redirect counts as exactly one click, including repeat clicks from the same client, with no de-duplication or bot filtering. _(source: assumption)_
  - AC-14.1: Given A newly created short link with 0 clicks, when The same client performs the redirect 5 times in succession with identical request headers and then requests analytics, then The analytics response reports a click count of 5
  - AC-14.2: Given A short link with 0 clicks and a nonexistent short code doesnotexist123, when A client requests the redirect for doesnotexist123 and then requests analytics for the existing link, then The existing link's click count remains 0
- **FR-15** [MVP] All operations (create, redirect, details, analytics) can be called without authentication. _(source: assumption)_
  - AC-15.1: Given The service is running, when A client sends create, redirect, details and analytics requests without any credentials or authorization header, then None of the responses has status 401 or 403, and each succeeds with its expected status (2xx for create, 302 for redirect, 200 for details and analytics)

## Assumptions

- **A-1** Short codes are always generated by the service; custom aliases are not supported (Q-1 default).
- **A-2** Submitting the same long URL more than once creates a new, independent short link each time (Q-2 default).
- **A-3** Only absolute http/https URLs are accepted on create; anything else is rejected with a client error (Q-3 default).
- **A-4** Details include the short code, the original URL and the creation timestamp; analytics (total clicks and last-click timestamp) are returned by a separate per-link call (Q-4 default).
- **A-5** Redirect, details and analytics calls return 404 Not Found for unknown short codes (Q-5 default).
- **A-6** A never-clicked link reports a click count of 0 and a null/absent last-click timestamp (Q-6 default).
- **A-7** Every successful redirect counts as one click, with no de-duplication or bot filtering (Q-7 default).
- **A-8** No authentication is required; all operations are public (Q-8 default).
- **A-9** Per C-1, 'reliability features' maps to no catalog entry, so no non-functional requirement is included until the user selects one or more catalog entries.

## Out of scope

- Rate limiting, contract input validation and Prometheus metrics NFRs (C-1 answered 'none')
- Uptime, failover and durability guarantees (cannot be built or validated per C-1)
- Permanent redirects (301/308); C-4 requires 302
- Custom short code aliases
- Updating or deleting short links (not requested)
- Link expiration (not requested)
- Per-click analytics beyond total count and last-click timestamp, such as referrer, geography or user agent (not requested)
- Click de-duplication or bot filtering
- User accounts or authentication (not requested)
- A user interface (not requested)

## Clarifications

- Which catalog capability does 'reliability features' refer to: per-client rate limiting on write endpoints (RL-BASIC), contract-based input validation with problem+json errors (SEC-INPUT), Prometheus request metrics at /metrics (OBS-METRICS), or none? Other reliability concerns, such as uptime, failover or durability guarantees, cannot be built or validated. → **none (no NFR is added until the user picks one or more catalog entries)**
- Which operations make up the 'core APIs'? → **Create a short link from a long URL, redirect from the short code to the original URL, and retrieve a short link's details**
- What should 'analytics' capture and expose for each short link? → **Total click count per short link, plus the timestamp of the last click, exposed via an API call for that link**
- Which HTTP redirect status should the redirect use: temporary (302/307) or permanent (301/308)? → **Use a temporary redirect (302) so every click reaches the service and is counted.**
